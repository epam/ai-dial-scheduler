# Phase 1 Data Model: Persist Conversation ID for Schedule Runs

**Spec**: [spec.md](./spec.md) | **Research**: [research.md](./research.md)

## 1. Schema change

### `schedule_runs.conversation_id`

| Property | Value |
|----------|-------|
| Column | `conversation_id` |
| Type | `VARCHAR` (unbounded — Postgres `varchar` with no length; no truncation of a real path) |
| Nullable | `NULL` (nullable) |
| Server default | none — SQL `NULL` is the "no conversation" value (research.md D1) |
| Python default | `None` |
| Index | none — the runs list filters by `schedule_id` (already indexed) and never queries by `conversation_id` |
| Backfill | none — pre-existing rows remain `NULL` (research.md D5) |

Model addition in `src/lib/models/schedule_run.py`, following the existing nullable-field style
(`end_time`, `result`):

```text
conversation_id: Optional[str]  →  Field(
    default=None,
    sa_type=String(),                       # unbounded varchar
    sa_column_kwargs={"nullable": True},
)
```

Docstring addition (in the class docstring `Attributes:` block):

> `conversation_id`: Addressable DIAL conversation id (`conversations/...`) for the conversation
> created for this run; `NULL` when no conversation was created (creation disabled, run not
> successful, in-progress, creation or persistence failed, or the run predates this feature).

### Unchanged but load-bearing

- The value stored is `DialConversation.id` (the full id including the `conversations/` prefix),
  which `build_conversation` already computes and reuses as the `PUT` target. The stored id and the
  written resource cannot drift because both derive from the same `conversation.id`.
- `status` / `end_time` / `result` semantics are untouched. `conversation_id` is orthogonal to the
  success/failure outcome (FR-006, SC-004).

## 4. Layer contracts

### Repository — `ScheduleRunRepository` (`src/lib/repositories/schedule_run_repository.py`)

| Method | Signature | Semantics |
|--------|-----------|-----------|
| `set_conversation_id` *(new)* | `(run_id: str, conversation_id: str) -> ScheduleRun \| None` | `session.get(ScheduleRun, uuid.UUID(run_id))`; if `None`, return `None`; else set `row.conversation_id = conversation_id`, `commit()`, return `row`. Same fetch-mutate-commit shape as `mark_success`/`mark_error`. |
| `list_for_schedule` *(unchanged)* | — | Already selects the full `ScheduleRun` ORM object, so `conversation_id` is loaded automatically — no query change. |
| `get_for_schedule` *(unchanged)* | — | Same — full ORM object, no change. |

No change to `create_in_progress` (id is `NULL` on creation), `mark_success`, `mark_error`, or
`mark_credentials_error`.

### Worker — conversation builder (`src/worker/conversation.py`)

`create_run_conversation` signature changes from `-> None` to `-> str`: after the successful
`put_conversation`, it returns `conversation.id` (the value already assigned to
`DialConversation.id`). The `logger.info("conversation_create_succeeded", ...)` line is retained.
No other logic changes; the id is only *returned*, never written to the DB here (research.md D2).

### Worker — job orchestration (`src/worker/jobs.py`)

`_maybe_create_conversation` captures the returned id and persists it inside the **existing**
best-effort `try/except` (FR-006):

```text
async def _maybe_create_conversation(ctx, credentials, properties, result) -> None:
    if properties.target_type != CHAT_COMPLETION or not properties.create_conversation:
        return
    try:
        conversation_id = await create_run_conversation(ctx, credentials, properties, result)
        async with Database().sessionmaker() as session:
            row = await ScheduleRunRepository(session).set_conversation_id(ctx.run_id, conversation_id)
        if row is None:
            logger.warning("conversation_id_persist_failed", run_id=ctx.run_id,
                           schedule_id=ctx.schedule_id, reason="run_record_missing")
        else:
            logger.info("conversation_id_persisted", run_id=ctx.run_id, schedule_id=ctx.schedule_id)
    except Exception as exc:
        logger.warning("conversation_create_failed", run_id=ctx.run_id,
                       schedule_id=ctx.schedule_id, reason=str(exc))
```

- A DIAL-creation failure raises before an id is returned → the persist line is never reached, run
  stays `success`, column stays `NULL` (FR-005/FR-006).
- A DB-persist failure is caught by the same `except` and logged; the run outcome is unchanged
  (FR-006, SC-004).
- The persist runs in its **own** session, opened after and independent of the success-marking
  session, so it can never roll back `_persist_success`.

### Service — `ScheduleRunService` (`src/lib/services/schedule_run_service.py`)

- `list_runs`: add `conversation_id=run.conversation_id` to the `RunListItem(...)` construction.
- `get_run`: add `conversation_id=run.conversation_id` to the `RunResponse(...)` construction.
- No signature, ownership, pagination, or ordering change.

### Endpoint — `src/api/v1/endpoints/runs.py`

No code change. `response_model=Page[RunListItem]` and `response_model=RunResponse` pick up the new
field automatically; the OpenAPI schema extends additively.

## 5. State (no new state machine)

`conversation_id` is a monotonic 0→1 write on top of the existing run status lifecycle; it adds no
status value and does not gate any transition.

```text
run created (in_progress)         conversation_id = NULL
        │
        ▼  mark_success
run success                        conversation_id = NULL
        │
        │  _maybe_create_conversation (chat_completion + create_conversation only)
        │
        ├── DIAL PUT succeeds ──▶ set_conversation_id ──▶ conversation_id = "conversations/..."  (terminal)
        │                              │
        │                              └── UPDATE fails (best-effort) ──▶ conversation_id = NULL (terminal)
        │
        └── DIAL PUT fails / disabled / non-chat / error / in-progress ──▶ conversation_id = NULL (terminal)
```

`mark_error` / `mark_credentials_error` never enter the conversation path, so failed runs keep
`conversation_id = NULL`. No path clears a non-null id back to `NULL` after it is set (FR-007).

## 6. Test case inventory (drives TDD)

**Model / migration**
1. `conversation_id` is nullable with no server default; a newly created run reads `None`.
2. Upgrade on a DB with pre-existing runs leaves every row `conversation_id = NULL`; downgrade drops
   the column.

**Schemas**
3. `RunListItem` serialises `conversation_id` when set, and as `null` when `None` (default).
4. `RunResponse` serialises `conversation_id` when set, and as `null` when `None` (default).
5. Both fields are optional — constructing the schema without `conversation_id` yields `None` (no
   validation error), proving backward compatibility.

**Repository — `ScheduleRunRepository`**
6. `set_conversation_id` sets the column on an existing run and returns the row; a re-read shows the
   value.
7. `set_conversation_id` returns `None` for an unknown `run_id` and writes nothing.
8. `set_conversation_id` does not alter `status`, `end_time`, or `result` (FR-006).
9. `list_for_schedule` returns runs carrying the persisted `conversation_id` and `None` for runs
   without one, in the same page.

**Worker — `conversation.py`**
10. `create_run_conversation` returns the same id it PUTs (`conversation.id`), with the
    `conversations/` prefix.

**Worker — `jobs.py` / `_maybe_create_conversation`**
11. Successful conversation creation → `set_conversation_id` called once with the returned id;
    `conversation_id_persisted` logged.
12. Conversation creation raising `ConversationCreationError` → `set_conversation_id` **not** called;
    `conversation_create_failed` logged; run stays `success`, id `NULL` (FR-005/FR-006).
13. `set_conversation_id` raising a DB error → swallowed, `conversation_create_failed` logged, run
    outcome unchanged (FR-006, SC-004).
14. `set_conversation_id` returning `None` (run row missing) → `conversation_id_persist_failed`
    logged; no exception.
15. Non-chat-completion or `create_conversation=False` → neither `create_run_conversation` nor
    `set_conversation_id` is called; id `NULL` (FR-005).

**Service**
16. `list_runs` maps `run.conversation_id` into each `RunListItem` (set and `None` cases).
17. `get_run` maps `run.conversation_id` into `RunResponse` (set and `None` cases).

**Endpoint / integration**
18. `GET /v1/schedules/{id}/runs` returns `conversation_id` for a run that created a conversation
    (SC-001) and `null` for a run that did not (SC-002).
19. `GET /v1/schedules/{id}/runs/{run_id}` returns the same `conversation_id` as the list entry for
    the same run (SC-005, consistency).
20. Listing the same run twice returns an identical, unchanged `conversation_id` (FR-007, SC-005).
21. End-to-end: a chat-completion schedule with `create_conversation=true` runs to success → the
    listed run's `conversation_id` addresses the created conversation (SC-001, SC-003); a run of a
    schedule with creation disabled and a failed run both report `null` (SC-002).
