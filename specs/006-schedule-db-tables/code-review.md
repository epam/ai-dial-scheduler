**Reference**: `migrations/versions/` (directory still does not exist); `tasks.md` T013 and T017 unchecked.

Re-verified this run: there is no `migrations/versions/` directory and no revision file. FR-016/FR-018
and SC-005 require an Alembic-autogenerated, reversible migration that creates both tables with PK,
named CHECK, RESTRICT FK, and index, and that never touches `apscheduler_jobs`. The models remain
migration-ready (separate unmanaged `MetaData` for `apscheduler_jobs` plus the `include_name` guard
in `migrations/env.py`), so this is a "run the command in a DB-available environment" gap, not a model
defect — but it is the single stated-intent deliverable not yet satisfied.

**Fix** (unchanged from the first review):
```
uv run alembic revision --autogenerate -m "create schedules and schedule_runs tables"
uv run alembic upgrade head && uv run alembic downgrade -1 && uv run alembic upgrade head
```
Before committing, confirm the generated script contains `CK_schedule_runs_status`,
`FK_schedule_runs_schedule_id_schedules` with `ondelete='RESTRICT'`, `IX_schedule_runs_schedule_id`,
and **no** `apscheduler_jobs` operation — with no manual edits (FR-016).

### I2 — Inconsistent column-definition style in `ScheduleRun` — Status: Resolved
**Reference**: `src/lib/models/schedule_run.py:45-48`

`schedule_id` now uses the file-uniform `sa_type=String(191)` + `sa_column_kwargs={"nullable": False}`
style instead of `sa_column=sa.Column(...)`. The whole model and `Schedule` now share one column-
definition idiom. Functionally equivalent (the FK still lives in `ForeignKeyConstraint` under
`__table_args__`), and the readability/inference trap called out previously is gone. **Resolved as recommended.**

### I3 — Behavioral CHECK-constraint test — Status: Resolved
**Reference**: `tests/integration/test_schedule_run_join.py:203-221`
(`TestScheduleRunPersistence.test_check_constraint_rejects_invalid_status`).

A live-DB test now inserts `status="bogus_status"`, asserts `sqlalchemy.exc.IntegrityError` on
`flush()`, then rolls back — directly exercising SC-002/FR-010 against the DB rather than by string
matching. The `try/finally` + `_cleanup` is safe here: the rollback discards the schedule insert, so
cleanup is a harmless no-op. **Resolved.**

### I4 — Four-status round-trip and in-progress NULL end_time coverage — Status: Resolved
**Reference**: `tests/integration/test_schedule_run_join.py:124, 146, 172`.

Three tests now cover the previously-missing US2 scenarios:
- `test_all_status_values_can_be_stored` — parametrized over all `ScheduleRunStatus` members
  (success/error/in_progress/missed), verifying store-and-read-back fidelity (SC-002).
- `test_in_progress_run_has_no_end_time` — in_progress run with `end_time=None`/`result=None`

- `test_run_can_transition_to_success_with_end_time_and_result` — in_progress → success update path
  with `end_time` + `result` populated (US2 scenario 2).
**Resolved.**
