# Phase 0 Research: Schedule & Run Persistence Tables

All open questions from the spec (notably A-005) are resolved below.

## R1. APScheduler 3.11.2 `apscheduler_jobs` table shape

**Decision**: Treat `apscheduler_jobs` as an externally-owned table with this shape:

| Column | Type | Notes |
|--------|------|-------|
| `id` | `VARCHAR(191)` | Primary key; the job id we mirror as `schedules.id` |
| `next_run_time` | `DOUBLE PRECISION` (float) | Epoch seconds; **NULL when the job is paused** |
| `job_state` | `BYTEA` | Pickled job; irrelevant to this feature |

**Rationale**: APScheduler's `SQLAlchemyJobStore` (already configured in
`src/lib/scheduler.py`) creates this table itself on first use. The `id` is `Unicode(191)`
(191 chosen for MySQL utf8mb4 index limits; on PostgreSQL it is `VARCHAR(191)`).
`next_run_time` is a float epoch column, **nullable** — paused jobs have no next run.

**Alternatives considered**: Reflecting the table at runtime — rejected as unnecessary
runtime coupling and slower; a static minimal `Table` definition (id + next_run_time) is
enough for the join and keeps tests deterministic.

**Implications**: `schedules.id` must be `String(191)` (R3). The join brings back a raw
float epoch; converting it to a timezone-aware datetime is a future consumer/query concern,
out of scope here.

## R2. Keeping `apscheduler_jobs` out of our migrations while still joinable

**Decision**: Define a **read-only SQLAlchemy Core `Table`** (`apscheduler_jobs` with only
`id` and `next_run_time` columns) on a **separate, dedicated `MetaData`** (not
`BaseSQLModel.metadata`), exposed from `src/lib/models/apscheduler_job.py` for use in join
queries and tests.

**Rationale**:
- `migrations/env.py` already excludes `apscheduler_jobs` from autogenerate via
  `_UNMANAGED_TABLES` + `include_name`. Putting the reference on a *separate* metadata is a
  second, defense-in-depth guarantee that autogenerate can never emit DDL for it (FR-017,
  SC-005), regardless of the `include_name` guard.
- A lightweight Core `Table` (not a mapped SQLModel) signals "we do not own this" and avoids
  accidentally registering it with the managed metadata.
- Only `id` + `next_run_time` are needed for the join; we deliberately omit `job_state`.

**Alternatives considered**:
- Mapping a full `ApschedulerJob` SQLModel on the shared metadata — rejected: invites
  autogenerate to manage a table the engine owns and adds columns we never read.
- Pure runtime reflection — rejected: adds an engine/DDL dependency to every query and
  complicates unit testing.

**Implications**: The join is expressed in SQLAlchemy Core/ORM (`outerjoin`) — no raw SQL,
satisfying the constitution.

## R3. `schedules.id` type — match the engine for cast-free joins

**Decision**: `schedules.id: str` mapped to `String(191)`, primary key, **application
supplied** (equal to the APScheduler job id), no autogeneration / no server default.

**Rationale**: FR-002/FR-003 — the id is logically equal to `apscheduler_jobs.id`
(`VARCHAR(191)`). Matching the type and length lets `schedules.id = apscheduler_jobs.id`
join without `CAST`. There is **no** real FK to `apscheduler_jobs` (FR-002): the engine owns
that table and rows may appear/disappear independently.

**Alternatives considered**: `TEXT`/unbounded `String` — works functionally but diverges
from the engine's column definition; `191` keeps the two columns identical.

## R4. Run-status enforcement (resolves spec A-005) — **the key decision**

**Decision**: Store `schedule_runs.status` as a **`String` column** with a **named
`CHECK` constraint** (`status IN ('success','error','in_progress','missed')`) declared in
the model's `__table_args__`. Provide a Python `ScheduleRunStatus(StrEnum)` in
`src/lib/db/enums.py` for type-safe application use. Do **not** use a native PostgreSQL
`ENUM` type.

**Rationale**: The hard constraint is "migrations are only Alembic-generated, **no manual
changes**" (FR-016) **and** fully reversible (FR-018, SC-005). Native PG enums break this:
- Alembic autogenerate emits the `CREATE TYPE` inline on first `create_table`, but the
  autogenerated **downgrade** (`op.drop_table`) does **not** drop the orphaned enum type,
  so a re-`upgrade` fails with "type already exists" unless the migration is **manually
  edited** to add `sa.Enum(...).drop(bind)`. That manual edit is exactly what FR-016 forbids.
- Adding a status value later also requires a hand-written `ALTER TYPE` migration.

A named `CHECK` constraint is rendered **inline inside the autogenerated `op.create_table()`**
(it is part of the `Table`'s constraints) and is removed cleanly by `op.drop_table()` in the
downgrade — **zero manual edits, fully reversible**, while still enforcing the value set at
the database (FR-010). The project's naming convention
(`"ck": "CK_%(table_name)s_%(constraint_name)s"`, see `models/base.py`) names it
deterministically.

**Alternatives considered**:
- **Native `sa.Enum` / PG ENUM** — rejected: violates the no-manual-edit + reversibility
  constraints (see above); also brittle for future value changes.
- **No DB constraint, app-level only** — rejected: FR-010 says status MUST be constrained;
  app-only validation is weaker and untestable at the schema layer.

**Implications**: `status` is `String` in the DB; the `StrEnum` is used in application code
and snapshots. Tests assert that an out-of-set value is rejected by the database.

## R5. JSON column type

**Decision**: Use PostgreSQL `JSONB` (`sqlalchemy.dialects.postgresql.JSONB`) for `trigger`,
`kwargs`, `result`, and `schedule_snapshot`.

**Rationale**: JSONB is the PG-native, indexable, queryable JSON type; the project is
PostgreSQL-only (A-009). Autogenerate emits `postgresql.JSONB` cleanly and reversibly.
Nullability per data-model: `trigger`, `kwargs`, `schedule_snapshot` are `NOT NULL`;
`result` is **nullable** (an `in_progress` run has no result yet — FR-009/FR-011).

**Alternatives considered**: generic `JSON` — rejected: loses JSONB indexing/operators on
PG; `Text` holding serialized JSON — rejected: no DB-level JSON semantics.

## R6. `schedule_runs.id` — UUID generation

**Decision**: `schedule_runs.id: uuid.UUID`, primary key, mapped to PG `UUID`, generated
**application-side** with a Python `default=uuid.uuid4`.

**Rationale**: FR-008 requires a globally unique id independent of the schedule. Client-side
`uuid4` avoids depending on a DB extension (`pgcrypto`/`gen_random_uuid()` would require a
`CREATE EXTENSION`, which complicates a clean autogenerated, reversible migration). No server
default keeps the autogenerated migration free of extension management.

**Alternatives considered**: server-side `gen_random_uuid()` — rejected: needs `pgcrypto`
extension DDL (extra, potentially manual migration concern); bigint identity — rejected:
FR-008 favors a globally unique, non-sequential id.

## R7. Foreign key & delete protection

**Decision**: `schedule_runs.schedule_id: str` (`String(191)`), `NOT NULL`, **indexed**,
foreign key to `schedules.id` with `ondelete="RESTRICT"`.

**Rationale**: FR-013 (DB-enforced FK) + FR-014 (block deletion while runs exist).
`RESTRICT` is the literal "on delete protect" from `db_tables.md` (A-007). PostgreSQL does
not auto-create an index for the referencing column, so an explicit index on `schedule_id`
keeps run-history lookups and the RESTRICT check efficient. FK name follows the convention
`FK_schedule_runs_schedule_id_schedules`.

**Alternatives considered**: `CASCADE` — rejected: would destroy run history (violates
FR-014/SC-004); `SET NULL` — rejected: orphaned runs lose their schedule linkage.

## R8. Timestamps & base model reuse

**Decision**: Both models extend the existing `BaseSQLModel`, inheriting timezone-aware
`created_at` (server_default `now()`) and `updated_at` (server_default `now()`,
`onupdate now()`), and the auto `__tablename__` (`Schedule` → `schedules`,
`ScheduleRun` → `schedule_runs`). `end_time` is an explicit **nullable** timezone-aware
`DateTime(timezone=True)` column.

**Rationale**: DRY + consistency with existing conventions (A-006). The auto-pluralizing
`__tablename__` already yields the exact names required by `db_tables.md`.

**Alternatives considered**: redefining timestamps per model — rejected (DRY violation).

## Summary of resolved unknowns

| Spec ref | Question | Resolution |
|----------|----------|-----------|
| A-005 | status: native enum vs constraint | **String + named CHECK constraint** (R4) — only autogenerate-clean, reversible option |
| A-002 | id type | `String(191)` matching engine (R3) |
| A-003 | run id | client-side `uuid4` UUID (R6) |
| A-004 | JSON type | `JSONB`; `result` nullable (R5) |
| A-007 | delete protect | FK `ON DELETE RESTRICT` + index (R7) |
| — | join without managing engine table | separate-metadata read-only Core `Table` (R2) |
