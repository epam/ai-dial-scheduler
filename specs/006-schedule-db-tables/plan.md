# Implementation Plan: Schedule & Run Persistence Tables

**Branch**: `006-schedule-db-tables` | **Date**: 2026-06-10 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/006-schedule-db-tables/spec.md`

## Summary

Add two project-managed PostgreSQL tables — `schedules` (queryable business metadata for
each APScheduler job) and `schedule_runs` (one row per execution attempt) — as
SQLAlchemy/SQLModel ORM models, plus a single Alembic **autogenerated** migration that
creates them. `schedules.id` is type-compatible (`VARCHAR(191)`) with APScheduler 3.11.2's
`apscheduler_jobs.id`, so a LEFT OUTER JOIN can surface the engine's authoritative
`next_run_time` without casting while never dropping metadata rows. `schedule_runs`
references `schedules` with an `ON DELETE RESTRICT` foreign key and stays self-contained via
a JSON `schedule_snapshot`. `apscheduler_jobs` remains owned by the engine and excluded from
our managed metadata. Scope is **models + migration only** — no API endpoints, services, or
repositories — plus a thin read-only `apscheduler_jobs` table reference and tests that prove
the join and the delete-protection contract.

## Technical Context

**Language/Version**: Python 3.14 (`requires-python = ">=3.14,<3.15"`)

**Primary Dependencies**: SQLAlchemy 2.0.50 (`[asyncio]`), SQLModel 0.0.38, Alembic 1.18.4,
APScheduler ~3.11 (job store owner, not modified), Pydantic v2, asyncpg (async) / psycopg2
(sync, used by APScheduler job store)

**Storage**: PostgreSQL (async via `postgresql+asyncpg`; APScheduler job store uses
`postgresql+psycopg2`)

**Testing**: pytest + pytest-asyncio (`asyncio_mode = "auto"`), pytest-mock

**Target Platform**: Linux server (Docker), worker + API services share `src/lib`

**Project Type**: Web service backend (multi-service: `src/api`, `src/worker`, shared
`src/lib`) — this feature touches `src/lib` only

**Performance Goals**: N/A for schema definition. Join supports indexed lookup of runs by
`schedule_id`.

**Constraints**:
- Migration MUST be Alembic-autogenerated with **zero manual edits** and **fully reversible**
  (FR-016, FR-018, SC-005).
- `apscheduler_jobs` MUST NOT be created/altered/dropped by our migration (FR-017); it is
  already in `_UNMANAGED_TABLES` in `migrations/env.py`.
- `schedules.id` MUST match `apscheduler_jobs.id` storage type for cast-free joins (FR-003).
- No raw SQL, no `assert` in production code, async I/O only, `ruff` + `mypy` gates.

**Scale/Scope**: 2 new tables, 1 enum, 1 read-only table reference, 1 migration. Run table
is the higher-volume table; indexed FK on `schedule_id`.
